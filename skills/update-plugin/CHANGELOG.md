# Changelog

All notable changes to the AgenticAI Plugin.

Format: Machine-readable. Each version is a `## X.Y.Z` section.

## 0.33.9

- **The architecture audit rated a documented rule's violation as a pattern, and filed the breaches under *What Works Well* (#91).** Measured across 25 real analyzer runs against a fixture whose documentation demands hexagonal architecture and whose code violates it throughout: where Phase 1 had read the violation as *the* pattern, analyzer 03 rated its consistency **B in 4 of 4 runs** and inverted the enforcement contradiction — not the code was wrong, the tooling was. Analyzers now carry a precedence rule: a documented rule outranks the pattern reconstructed from code, including Phase 1; a contradiction between the two is a finding in its own right; and a breach of the documented architecture never belongs under *What Works Well*. The same six lines flipped the rating to **E/E/E/D in 4 of 4**.
- **The issue proposed the change in the place where it does nothing.** Phase 1 found the documentation-versus-code contradiction in **7 of 7** runs unaided — even with the docs kept out of the file list and the enforcement tooling unmentioned; one run inferred the rule from a comment in a dependency-cruiser config. Adding the same text there produced no measurable effect, because the baseline was already 100 %. Following the issue would have hardened the working half and left the broken one.
- **Two of its three complaints were dropped rather than built.** The missing notion of *change* is real but has no measured cost, and an eighth dimension would drag `WEIGHTS`, the rating table and the report structure behind it while shifting the overall grade. The enforcement-reach complaint was found unaided in **25 of 25** runs — all except one part: which expected rules are covered by *no* test at all. That part is now one bullet in analyzer 03, section 3.5, because partial enforcement reads like full enforcement until the gap is named.
- **The new assertion was confirmed to bite.** Removing the precedence block turns the suite red (`EXIT=1`, exactly the two new tests failing, no others); restoring it returns 276/276 at `EXIT=0`. One test covers the Phase-1-unavailable path, so the rule reaches the prompt in both branches.

## 0.33.8

- **The tracker skill picked issues without ever looking at their labels.** It cuts blocks out of what is open, and "open" was the whole filter — so an issue the owner had set aside was indistinguishable from one waiting to be worked. It now reads the labels first: `with-owner` may be assessed but never implemented alone, `deferred` is out of scope until reactivated, and the two are independent.
- **A word in the title is not a marking, and this repository proved it.** Issue #92 read `ZURÜCKGESTELLT:` in its title, carried no label for months, and kept showing up as normally selectable. Nothing checked — the rule that the label exists for lived in no text at all: a repo-wide grep for it returned exactly one hit, in a gitignored planning file. The skill now says this in the place where the mistake is made, and asks that a missing label be named out loud rather than handled silently.
- **Projects that name their labels differently are told to learn them first** rather than treat everything open as fair game; a project with no such labels should say so instead of assuming.

## 0.33.7

- **The autoskill reviewer's write cage answered "yes" in the two cases where it did not know (#122).** `read-guard.mjs` let a `Write`/`Edit` through when the tool input carried no `file_path` — no path, no decision, so no denial — and it kept guarding when `AUTOSKILL_STAGING_DIR` was absent, where `STAGING_DIR` falls back to a fixed path that `lib.mjs` itself marks predictable and world-readable (CWE-377): the cage would then guard a directory nobody prepared, refusing every write to the real staging dir while waving one into the fallback. Both now deny, and both say which of the two it was. Reads stay allowed in the second case — blocking them buys nothing and would break the read-before-write invariant.
- **The fix sits in the guard, not in `lib.mjs`.** The fallback is also the tests' isolation point (`lib.test.mjs:85` pins it), so removing it would have traded one defect for a broken harness. The library keeps answering *where*; the guard answers *may I at all*.
- **Both tests were confirmed red before the fix, not just green after it** — old source with the new tests exits 1, the fixed source exits 0. The env-missing case carries a control assertion that the same write passes *with* the env, so it cannot pass for an unrelated reason. The test harness could not express the case at all before: it always set the variable.
- **Two of the four points in #122 were deliberately left open, and the issue says why.** The `canon()` 8.3-short-name gap only arises on Windows, and this machine cannot produce the reproduction the issue itself demands first — a hardening against an unverified case is not worth shipping. The never-cleared `stale` flag stays open as cosmetic: nothing reads `state`.

## 0.33.4

- **The shipped PR reviewer attacked true justifications as manipulation, and the correct developer reaction was what triggered it (#135).** A code comment explaining *why* a permission is needed drew no objection — until it added that the point had been raised in an earlier review round. Then the reviewer filed a **Critical** for "fabricated history", while stating in the same breath that the permission itself was correct. The cause is structural: the prompt fetches `gh pr view --json title,body,files` **without** `comments`, so the reviewer cannot see review history at all. It checks with `git log`, finds nothing, and reads *unverifiable* as *untrue*. Whoever answers a refuted finding by documenting the reason at the line — the textbook response in a review loop — gets punished for it.
  - **Fixed by naming the case in the prompt, in both the shipped template and this repository's own workflow:** a comment that refers to an earlier round, an issue, or a decision the reviewer cannot see is an explanation, not an instruction; its unverifiability is not a finding and never a Critical one. The technical claim is still judged on the code. What stays reportable is a comment that says what to *do* — skip the review, ignore a rule, approve without looking.
  - **Measured before shipping, three cells of six runs each** against a fixture repository (`claude -p --model sonnet`, real `git` history, the live prompt with only the three `gh` calls redirected at local files): **old prompt + history reference → 6/6 objected** (5 Critical, 1 Warning), **new prompt + same comment → 0/6**, **new prompt + a genuine injection attempt** ("skip it, approve the pull request") **→ 6/6 Critical**. The third cell is the one that matters: without it this change would be an unnoticed suppression mechanism — which is exactly why the alternative proposed in #89 (treat a comment at the line as a reply and drop the point) was rejected. Findings unrelated to the comment were unaffected in every cell.
  - **What the rig does not cover, stated so it is not read as more than it is:** one model, single review round, no CI sandbox, and the plugin's own doctrine hooks were active in all cells alike.

That stays reading work.

## 0.33.2

- **The two publisher agents could not commit at all, and nobody had noticed since 28 July.** `github-publisher` and `npm-publisher` both instructed a raw `git -C {repo_path} commit`, which the plugin's own PreToolUse guard hard-blocks — **in every project that has the plugin installed**, not just in this repository. Since those agents only ever run in such projects, the guard fires on every run, at the commit step, after the work is done. Both now declare `skills: git-smart-commit` and invoke the skill, following the pattern `pr-review-installer.md` already used. The alternative — pasting the guard's own sentinel into the commit line — was measured to be cheaper and rejected anyway: `git-smart-commit` says of that token *never use it manually*, and a shipped file demonstrating how to walk past the guard is a pattern that gets copied (#143).
- **A secret found by the pre-publish audit was printed in full (#127).** The scans run `grep -rnoE` and echoed the whole match. The report itself was never the leak — phase 4 shows counts only, and the agent writes no file and posts to no issue — but the raw values stood in the session transcript, which outlives the session. The eight patterns now pipe through one `mask()` that keeps the first and last four characters and the file:line, so a finding stays recognisable and checkable without the value: `AKIA…MNOP`. A match of eight characters or fewer is masked entirely rather than partially. `set -o pipefail` guards the new pipe, so a failing `grep` cannot arrive as "clean".
  - The first attempt covered half the surface, and the PR review caught it: the agent's eight commands are an *excerpt* of a fifteen-row catalog in the reference, six rows of which have no command of their own and are declared runnable-as-written. Anything assembled from those rows printed plaintext again. The catalog now requires every command built from it to pipe through the same `mask()` — referenced, not copied, so there is one definition to change.
- **The release changelog silently covered the wrong range (#128).** `LAST_TAG` was set in one bash block and read in another; shell state does not survive that, so the variable was empty, `RANGE=HEAD` took over, and every commit in the repository's history went into the changelog — indistinguishable from the documented case "no tag exists yet". It is now re-derived where it is used, the way `PKG_NAME` already was. The same block's source-map scans piped `find` into `while` and dropped the exit code; `set -o pipefail` restores it — smaller than the file-based rewrite the issue proposed, and a pattern the file already used twelve lines earlier.
- **`gh`, `curl` and `tar` are now declared prerequisites.** The registry knew `node` and `claude`; everything else was assumed present, and a missing tool surfaced as a mid-skill failure rather than a startup notice. **What is deliberately not registered:** the project-dependent tools (mvn, gradle, cargo, go, pip, dotnet). Warning someone about a missing `cargo` when they have no Rust project is noise, and gating them needs a marker mechanism this repository is not buying — it has already shipped one whitelist whose only measurable effect was a defect. The developer documentation now states the corollary: a registry entry does not replace naming the tool in prose where it is invoked, because the startup notice fires once, before the skill runs.
- **`markdown-converter` claimed "no installation required".** It calls `uvx markitdown`, which needs `uv` on PATH.
- **The secret scan aborted on every Mac, and the check written to prove otherwise is what found it (#125).** A throwaway matrix job ran the patterns on `ubuntu-latest` and `macos-latest`, **extracting them from the markdown at runtime** rather than transcribing them, so no copy could drift from the source. Seven patterns passed. The eighth — the generic high-entropy catch-all — died: `grep: maximum repetition exceeds 255`, **exit 2**. Its bound was `{16,512}`, and BSD grep hard-caps repetition counts at 255. On macOS this CRITICAL scan never ran at all; it did not report "nothing found", it aborted the step. The bound is now `{16,255}`, which changes nothing about coverage — the cap only truncates what is printed, and a 400-character value still matches and is still reported (verified).
  - **The rationale for that bound cited two different measurements for the same claim** — 647 B in the reference, 215 B in the agent file — and 215 B is not reachable for a match greedily capped at 512 characters, so it was never measured at all. Both now carry one re-measured figure: **265 B**, against 1,500,136 B unbounded.
  - Worth naming: three lines above the failing pattern sits a comment choosing `[[:space:]]` over `\s` *because BSD grep reads the latter as a literal `s`*. BSD was considered — at one spot, three lines from the one that broke there. A review reading for portability would have passed this file; only running it on the platform found it.

## 0.33.1

- **The delegation rules now say that your own task prompt can be wrong, and that the agent may say so.** They covered one direction — *"agent reports are hints, not proof"*, the orchestrator distrusting the report. The other was nowhere: a brief carries assumptions (a path, a scope, a criterion), and the agent executing it is the one positioned to catch them. **Measured while working an issue block:** six briefs in one session named a wrong file path, too narrow a scope, an error criterion that conflated a parse failure with a legitimate `null`, and an undercounted number of occurrences. **The executing agents caught all six; the author caught none** — and only because each prompt happened to include "refute my premises if they do not hold". That was a habit, not a rule, and the next session did not inherit it. It does now. **What you will notice:** agents come back with corrections to what you told them, not just with what you asked for. Costs 365 B per session, roughly what removing the unreachable sub-agent clause in 0.33.0 saved — the trade is deliberate, because that clause addressed readers who never received it and this one addresses the session that does.

## 0.33.0

- **New command `/agenticaiplugin:tracker` — works a backlog in blocks instead of issue by issue.** Map how the issues couple *before* cutting any block, because the coupling is usually not in the files: two issues can be file-disjoint and still collide because both release, both touch a generated artifact, or both move citations a test resolves. Evaluate each issue with one agent per issue, in parallel, and **reproduce rather than read** — build the case, run the command, feed the parser a real input. Then hand the block to the owner before implementing, and every pull request to the owner for the merge. The skill was written from a run in this repository where **four of six issues turned out smaller than their own description** and none was implemented the way its body proposed: one was closed unbuilt, one had its defect in a different file than the title claimed, one turned from a deletion into a move. The evaluation step is what found that, and it cost a fraction of building the six issues as written.
  - **Post each evaluation into its issue.** What is not written down is gone with the session, and the next round starts by measuring it again. The rule was paid for: a full council plus 108 measured runs once reconstructed an assessment that had been sitting in the issue's comments for two days.
- **A configuration file that cannot be read now says so, instead of quietly switching off what you turned on (#119).** Measured across 17 shapes of `agenticaiplugin.config.json`: a stray BOM, a missing comma, a directory in place of the file — every consumer falls back to its default, and for `autoskill` that default is **off**. The one channel that would have shown you it stopped working (the review notice) goes with it. The doctrine's behaviour was the harmless half the issue described: it stays injected, only the opt-out is lost. The guard is self-announcing anyway — it stays on and blocks the next commit with a message that names the key. `check-prereqs.mjs` now emits a `systemMessage` — **visible in your terminal, not in the model's context** — naming the reason: `cannot be read (EISDIR)`, `is not valid JSON (…)`, `does not contain a JSON object`. It is deliberately not debounced: the prerequisite notice repeats a state you often cannot fix, a broken config is one only you can, and going quiet after the first session would recreate the exact failure the warning exists to end.
  - **What it deliberately does not catch, stated in the code so nobody "fixes" it later:** a typo in a key (`{"autoskil":…}`) or a wrong value type (`{"doctrine":"off"}`). Those parse, stay silent, and stay ineffective. Catching them needs a list of known keys kept in sync with the README — a drift surface this hook is not worth, and this repository has already shipped one whitelist whose only measurable effect was a defect.
- **`skills/learn` and the autoskill prompts enforced a rule that does not exist, and were silent about the one that does (#112).** They demanded descriptions of at most 60 characters because "the skill index truncates at 60". It does not — measured: descriptions of several hundred characters arrive intact. The real hazard is YAML, and it was written down nowhere: in an unquoted scalar, ` #` **ends the value** (everything after it is a comment) and `: ` is a **parse error that takes the whole frontmatter with it**, not just the line. Nine shipped descriptions contain one of those sequences today and survive for a single reason — they happen to be written as block scalars. The next one written plain loses its frontmatter. All three places now say what to do (quote it) rather than enforcing a fiction, and `repo-hygiene.test.mjs` fails on a plain-scalar description carrying either sequence.
- **The doctrine dropped a paragraph that addressed an audience which never receives it.** The `No Workflow tool (sub-agent/fork)` block instructed sub-agents, and injected doctrine measurably does not reach a freshly started sub-agent — about 500 B per session spent on readers who never see it. **Nothing was lost:** the handover checklist now lives inline in `skills/code-review/SKILL.md`, which *is* loaded at the moment the check is due, and the fork's spawn prohibition already stands in the shared delegation rules. What does reach sub-agents is the enforcement: the commit guard fires there and names the replacement path in its denial, at zero prompt cost.
- **`/agenticaiplugin:pr-review-setup` no longer forces a line number the reviewer may not have.** The template demanded `file:line` on every finding, so a model without a line invented one — line 646 in a 319-line file is not arithmetic, it is fabrication. Findings may now be reported per file, and the citation form is described rather than compelled. Removed as well: a paragraph telling the reviewer to treat a comment at the faulted line as an instruction — the one place that granted a PR-controlled text authority over the reviewer, in a workflow that runs with write permissions in other people's repositories. 108 measured runs showed it prevented nothing and helped nothing.
  - The generated workflow's own guard was leaking in three places that all exited 0: an unset `GITHUB_WORKFLOW_REF`, a reference yielding no usable path, and the 3000-file API cap — each reported "workflow untouched" for a case it had never seen. A renamed workflow file was invisible to it. The post-render check verified the shape of the git allow-list rather than its contents.
- **`/agenticaiplugin:license-check` and `/agenticaiplugin:npm-publish` got their scanners corrected** — a gradle abort that hid a legitimate cause, and secret-scan patterns that missed real matches after the POSIX conversion.
- **Developer documentation:** `docs/rules-howto.md` is gone; its one still-valid section moved verbatim into `docs/architecture.md`, which now carries the third doctrine summary. The frontmatter reference no longer claims `name` and `description` are required for agents (three agents run without any frontmatter at all) nor that the `skills:` field matches a `name:` field — it matches the skill's **directory** name, and none of the 25 shipped skills carries a `name:`. `${CLAUDE_PLUGIN_ROOT}` is empty **as a shell variable only**; in `hooks.json`, `SKILL.md` and `agents/*.md` bodies it is substituted, which is why every hook starts at all.

## 0.32.0

- **The doctrine now argues against its own growth: where several solutions would work, the smallest wins, and proposing a larger one requires naming the concrete failure case that rules the smaller one out.** The rule was paid for. A concept in this repository grew over a full day into an architecture rebuild — a duplicated file structure addressed by audience, type markers in rule files, five structural tests, a presence hook — all of it descended from one finding whose actual remedy is a single line in a task prompt. A review agent then returned 18 findings on that concept, 16 of them correct, and **not one** said the concept was larger than the problem it solved: it had been asked whether the thing was built right, never whether it should exist. The owner stopped the concept. This sentence is what would have stopped it earlier, and it sits under `Surgical, minimal scope` rather than beside it, because it is that rule with teeth. **What you will notice:** a proposal to build the bigger thing now carries a burden of proof, and "it is cleaner this way" does not discharge it.
- **The orchestrator got an escalation ladder, and with it a way to answer questions instead of forwarding them.** Three rungs: decidable by measurement → measure, decide, record how; arguable from evidence but not measurable → get a second view, decide, state the reasoning, mark it revisable; preference, scope or cost → the owner's call, present the options and stop for the decision. Asking when it leaves you unsure closes the ladder rather than forming a fourth rung — it is explicitly allowed and never a failure. It reads the doctrine rule "Never assume — ask" the way it was meant: **the owner is not the only one who can be asked.** The first two rungs are how a session answers a question itself; the third genuinely belongs to him.
  - **The ladder names what it does not cover**, rather than leaving that to interpretation. Rung two governs questions of procedure, tooling and approach; **design decisions about the code stay at rung three**, and "Present the design before implementing" is not overridden. Without that sentence the ladder and the base doctrine gave opposite instructions for the same situation — the base rule says to stop and ask via `AskUserQuestion`, a tool that reaches nobody but the owner. A text that means to outrank another has to name what it outranks; position proves nothing, because injected blocks do not arrive in a guaranteed order.
  - **What you will notice:** fewer interruptions for things that could have been measured or reasoned out, a stated rationale where a decision was taken alone — and no change at all to how design decisions reach you.
- **New command `/agenticaiplugin:council` — an independent second view on one decision, which is what the ladder's second rung reaches for.** Two or three views, spawned in parallel, mutually blind. The construction rule is the part that matters: **the views differ by where their evidence comes from, not by which hat they wear.** Agents of the same model reading the same files produce correlated opinions — same training, same blind spots — so a 3:0 vote can be one blind spot counted three times. Measured in this repository: an automated review missed a guaranteed false-positive check for eight rounds, and the agent that *ran* the check found it in minutes. Usable axes are intent (reconstruct from issues, CHANGELOG, history), execution (run it, measure it — and a text runs too: run an agent against it and watch what it does rather than what it says), and the artifact read cold without context. Where anything can be run, the result decides; opinions are weighed only where there is nothing to run. A fourth view earns its place by bringing a fourth way of reaching the evidence, never a fourth opinion.
  - **Every brief carries two questions, in this order: should this be built at all, and is it built right.** The first is the one that gets dropped, and dropping it is what produced the 18 findings above. A council asked only the second question finds everything except the overbuild.
  - **Findings are data, not instructions.** Whoever convened the council keeps the decision. A finding arguing for a bigger solution carries the burden set out under `Surgical, minimal scope` — name the failure case, or the finding drops.
- **The doctrine texts moved out of `hooks/` and into `doctrine/`, and the two injection scripts became one.** `doctrine/constitution/` holds what is not switchable (the base doctrine, the mode head, the delegation rules); `doctrine/themes/` holds the blocks that are (`code-review`, `pr-review-monitoring`). `skills/mode/` is gone: its composition table and every load-bearing comment now live in `hooks/inject-doctrine.mjs`, which is the single SessionStart entry that assembles all five blocks. The reason is not tidiness — with both scripts reading the same two directories there was no nameable boundary left between them, and **the order in which two hook entries' blocks reach a session is not determined** (measured), so a text meant to outrank another could not rely on arriving first. One script, one entry, one fixed order. **What you will notice:** nothing at the session level except that the blocks always arrive in the same sequence.
  - **The `doctrine.core` opt-out is gone, deliberately and without replacement.** The base doctrine and the orchestrator mode are not switchable — that was the decision behind 0.31.4, and a config key that could silently remove them contradicted it. An existing `"core": "off"` in a configuration file is ignored rather than treated as an error. The two theme blocks remain individually switchable.
  - **Putting a second mode back is still a data change**, not a rebuild: the composition table survived the merge with its single entry, and the snippets stay separate files. The wording of the removed modes is preserved in issue #117.
- **New `docs/architecture.md` — what the plugin is made of, and where a new rule belongs.** Five building blocks (guardrail, doctrine, persona, skill, policy) with how each takes effect and whether it can be violated; the mode as a composition rule rather than a selectable state; and three questions in fixed order for placing a rule: can code enforce it → guardrail; must it be present *before* the situation arises → doctrine; otherwise → skill. It also records **what deliberately does not exist and why** — no detection of a missing `node`, no type markers, no structural tests, no presence hook — because an absence that is not explained reads as an oversight and gets built by the next reader. A glossary is included. Measurement setups and raw numbers stay in issue #114; what lands in whose context stays in `docs/context-map.md`.

## 0.31.4

- **There is only one working mode now — `orchestrator` — it is active in every session, and there is nothing left to switch (#117).** `task` and `meta-orchestrator` are gone, and with them the `/agenticaiplugin:mode` command, the `mode.state` file and the `agentMode` opt-out. The reason is the context window rather than the modes themselves: an injected block is append-only, so switching a mode mid-session does not replace the previous text, it adds to it — and the session then holds two mutually exclusive descriptions of who executes the work, with no way to tell which one is meant. Every switch was one such collision waiting to happen; a mode that cannot be switched cannot produce it. **What you will notice:** the delegating mode text arrives at every session start, including after compaction, without anyone having set anything, and there is no configuration key that turns it off.
- **The mechanism survived the removal intact.** `mode.mjs` keeps its composition table and its injection path, the mode head and the shared delegation rules stay separate files, and the filename whitelist still guards every path that reaches the file system. The table simply has one entry — putting a mode back is a data change plus a snippet, not a rebuilt script. The wording of both removed modes is preserved in issue #117, so nothing that was learned in a real run is lost.
- **The doctrine dropped its override clause**, which allowed a mode text to draw one of its rules tighter or wider. It was written for `meta-orchestrator`'s escalation ladder and had no other user; leaving a permission in the always-on doctrine that nothing exercises invites a future reader to invent a use for it.

## 0.31.3

- **A sub-agent that ends without a report looks exactly like one that had nothing to say — and the delegation rules said nothing about that case.** Measured in this session: an agent that is *spawned* returns its result on its own, but one continued **via SendMessage has no automatic return path at all** — its closing text goes nowhere. ## 0.31.2

- **The autoskill curator has been running weekly for months and never once marked a skill stale — because the clock it read was one it kept resetting itself.** For a skill with no recorded usage the lifecycle pass fell back to the `SKILL.md` mtime, and every patch by the background reviewer refreshes exactly that timestamp. ## 0.30.1

- **⚠️ Behaviour change, and the one you will notice first: a pull request that changes `claude-review.yml` *together with other files* now fails its check, red, where 0.30.0 let it pass green (#94).** This is not a defect in your setup. The review action refuses to run whenever that file differs from the version on your default branch — otherwise a PR could rewrite its own reviewer and then be reviewed by the rewritten version — and until now it exited **green** while doing so. Every other file in such a PR lost its review with it, invisibly. **The way through is two pull requests, in this order:** land the workflow change on its own and merge it, *then* branch the rest off the updated default branch. The order is the part people get wrong — byte-equality is checked against the default branch, not against your PR's base, so stacking the second PR on the first leaves it skipped just the same. The job summary spells this out on the failing run; you do not have to remember it.
  - **A workflow-only PR still passes green** — deliberately, because there the skip is unavoidable and the remaining unreviewed diff is the one file a human has to read anyway. It now says so in a notice and in the job summary instead of looking like a review that found nothing.
  - **The PR that first installs the workflow also stays green**, together with anything it brings along, since no review can run before the file reaches the default branch. What changed there is only honesty: the summary now names how many other files went unreviewed with it, rather than mentioning the workflow alone.
  - **The guard reads its own path from `GITHUB_WORKFLOW_REF` rather than a fixed string**, so renaming the workflow in your repository cannot quietly disarm it. A guard pointed at a path that no longer exists matches nothing — and "matches nothing" is exactly what it reports as *untouched*.
  - **An empty file list from the pull-request API aborts the run.** Every PR has at least one file, so an empty answer is a lookup that failed, not a workflow left alone. Suppressing that distinction is the failure class the last three releases have been removing; a guard against silent passes that can itself pass silently would be worth little.
- **Agents no longer read a green check as a completed review.** The always-on PR monitoring gained one sentence: a run that posted no findings comment was skipped or died quietly and is reported as a failure, not as approval. Phrased by what is missing rather than by any one cause, so it also covers projects that have not installed the guard, and silent failures nobody has catalogued yet.
- **The `npm-publish` tarball audit was not merely verbose — its e-mail scan never finished, while the address it was looking for sat in the file (#86, groups A and B).** A published tarball is mostly minified code, where a whole file is one line; the pattern's unbounded `+` before an anchor made the scan quadratic in line length and it was killed after 45 seconds. A secret scan reporting nothing because it was killed is worse than a slow one. The remaining scans stopped printing the file around the finding: absolute paths 2.8 MB → 37 KB, IP addresses 1.4 MB → 134 B, hostnames 1.4 MB / 41.6 s → 281 B / 0.6 s.
  - **Bounds were added only where measurement demanded them**, because tightening the others *costs findings*: a bounded first JWT segment leaves no room for the `.` that must follow it, and the technically correct 63-character DNS limit turned a 100-character hostname label from found into not found. Hit locations were diffed before and after across all eleven pattern classes over normal, minified and `.map` files, and are identical.
  - **A licence check could report four of six dependencies and call the result complete — in three ecosystems (#99).** Maven, Gradle and .NET each had a parser that dropped a line it could not read instead of saying so, which is the most expensive failure in this release: not a missing tool you would notice, but a scan that looks clean while a package's licence was never examined. Gradle lost two everyday shapes — a rich version constraint (`{strictly 2.0.13}`, where the brace ends the coordinate's third field early) and a dependency carrying **no version in the build file at all**, because a BOM supplies it, which in Spring Boot projects is the normal case rather than the exotic one. The version is now taken from behind the arrow wherever there is one, since that is what actually lands on the classpath, and a coordinate-shaped line that yields no version aborts instead of disappearing. .NET discarded every entry whose version was unresolved; those now show up as unresolved rather than vanishing — the same treatment `npm ls` already gave a platform-specific optional dependency a release earlier. An unresolved entry is routine in a multi-project solution, so aborting there would have been wrong; hiding it was worse.
  - **Four ecosystems could no longer tell "nothing ran" from "nothing found" in the licence check** — `gradle`, `./gradlew`, `dotnet` and `pip`/`npm` each returned an empty result with the explanation discarded, so a missing tool read as a clean scan. **Maven needed the opposite treatment**: it writes its whole log, failures included, to *stdout*, so suppressing stderr hid nothing while implying the failure path was handled. Against a cold local repository one dependency produced 144 KB in 458 lines, of which 442 were download progress and 3 were the answer.
  - **`pip show` reported packages as licence-less that do carry one.** `setuptools` and `wheel` print an empty `License:` value and declare MIT only in the classifier block that `-v` prints. Two MIT packages were being reported as undeclared — and an empty answer being *common* here is precisely why it must not be conflated with a failed lookup.
  - **Two sites are marked as unverified against a live tool, in the file itself**: `gradle dependencies` and `dotnet list package` are not installed in the verification environment. Their failure form was measured and their parse checked against sample output in the documented format; their parse against a real project's output was not.

The version-mismatch example in the `npm-publish` reference kept its lesson and lost the project name, version numbers and internal file path — for a reader outside that project they carried no information, only its internals.

The former check 8 is now **8a** (unchanged); new **8b** reports this as **informational** — not a leak, just useless — into a new `sourcemaps_unreachable` bucket. The overlap with the absolute-path scan (check 1) is deliberate: there an absolute path matches as a raw path string (Critical, build-environment leak), here as the semantic statement that the map points out of the package. One line may legitimately produce both findings; they are not deduplicated.

## 0.26.6

- **Fix: the review doctrine made sub-agents fan out further sub-agents and stall (#50).** The `Workflow` tool is only available in the main session. ## 0.26.5

- **Two new review/test checkpoints from a bug that six milestone gates missed (#49).** A service wrote video records inside a still-open transaction and, from within it, kicked off async thumbnail downloads running in their own threads and therefore their own transactions. The download succeeded and the file landed on disk; the worker's follow-up flag update looked the record up in its own transaction, could not see the uncommitted rows, and got an empty `Optional`. The write path was `Optional.ifPresent(v -> v.setThumbnailDownloaded(true))` — an empty Optional means the lambda simply does not run. No error, no exception, no log: file present, flag false, tests green. No gate caught it (the compiler cannot, the tests only asserted "file exists", and `Optional.ifPresent` in isolation is exactly the recommended null-safety idiom — it turns dangerous only through the thread/transaction context).
  - **New rule 8.8 "Silent No-op Writes Across Isolation Boundaries"** in `specialists/08-cross-cutting-concerns.md`. Hit precision is the whole point here — the pattern occurs dozens of times in any codebase, almost always harmlessly in read paths — so **both** triggers must apply: the conditional branch performs a *write* (state mutation, persistence, filesystem, outbound call), **and** the path crosses an *isolation boundary* (own thread, own transaction, async execution, process/service boundary). The finding is that the no-op is unobservable — no log, no metric, no assertion covers the empty case. WARNING by default, CRITICAL only when the skipped write is a state marker other code relies on; read paths, single-transaction synchronous code, and already-logged empty branches are explicitly **not** findings. Formulated language-agnostically (Java `Optional.ifPresent`, JS optional chaining with a side effect, Python `dict.get()` writes, Go `if v, ok := m[k]; ok`, ignored `UPDATE … WHERE` row counts, `filter(...).forEach(write)`), with the Java case as illustration only.

Where a feature consists of an artifact **plus** a state marker recording it (file + "downloaded" flag, message + "notified" timestamp, record + import status), both belong in the definition of done.

- **New skill: handover.** Cross-session continuity mechanism that complements auto-memory with a temporal snapshot ("where was I, what's open, what's next") instead of persistent semantic facts.
